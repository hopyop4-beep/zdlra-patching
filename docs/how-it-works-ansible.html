How the Ansible version works

A walkthrough of the ansible/ folder on main: what runs where, which task file includes which, and what happens when something breaks. It is the companion to how-it-works.html, which covers the shell scripts. The two versions do the same patch in the same order, and keep the same files on the node. Do not mix them within one run.

Status: tested only on a stand-in appliance, not yet on a real one.

Ground rules the code is built around

Long commands are never killedracli, patchmgr and the Oracle precheck run detached on the node, through zdlra_detached.sh. Ansible only starts them and polls them.
Nothing runs twice by accidentA command still running is waited for. A result an earlier attempt left is used. Versions are read before any repeat patch.
Files hold the stateThe run folder on the node, plus one JSON file on the jump server. Ansible can stop at any point and be run again.
No change without approvalPatch phases refuse unless the precheck is approved, under 24 hours old, real, and unchanged.
Dry run by defaultOnly -e zdlra_execute=true changes anything. --check is a dry run too.
On failure, stop and holdThe rescue records where it failed. Blackout and suspended jobs stay in place until you decide.
changes somethingmain stepguard or stopyou, or a side note

1. Who runs what

Everything starts on the jump server (the OMS host). There is no script on the node to drive the run: Ansible connects over ssh as root and runs each task there. Two small helper scripts are copied to every compute node at the start of each run, because some work must outlive the ssh session or must keep a password off the command line.

2. A full run, start to finish

One playbook run goes through every step below, in this order. Each green box is a phase with a tag of its own; you can pick phases with --tags but not reorder them.

3. The playbooks

zdlra_patch.yml

One play, on <zdlra>[0], with gather_facts: false, check_mode: false and any_errors_fatal: true. Check mode is off on purpose: read-only commands (racli status, imageinfo, SQL queries) must give real answers in a dry run too. What changes is decided by zdlra_dry_run instead, which --check also sets.

  1. Setup (import_role ... tasks_from: setup, tagged always). Checks the appliance was named and is an inventory group, the user is root and racli is there. Copies the two helpers to every compute node. Picks the run: zdlra_run_id if given (its folder must exist), otherwise a new ID from the node's clock. Creates the run folder and the controller folders, then reads the staged record, the patch.conf_<SR> it names, and the run's own records (read_state.yml).
  2. The patch, one block with a rescue. Each phase is an include_role ... tasks_from: run_phase with apply: {tags: [<phase>]} and the condition '<phase>' not in zdlra_skip_done. zdlra_skip_done is the run's phases_done less anything listed in zdlra_rerun. So running the same command again carries on where it stopped.
  3. OEM steps sit between the phases, tagged oem: a check before the precheck, then (after approval) blackout and jobs suspended, then at the end jobs resumed and blackout ended. A run whose OEM finish already happened is refused, unless its patching is complete.
  4. The end: finish.yml on success, failed.yml in the rescue. Both are applied with tag always, so a run limited with --tags still records its outcome.

oem.yml

A play on localhost that takes oem_action: targets, check, status, start, stop, suspend_jobs, resume_jobs or finish (resume the jobs, then end the blackout). It reads oem_blackout_targets and oem_jobs_db from the appliance's inventory group. Use it to fix up OEM by hand, for example after abandoning a failed run.

zdlra_status.yml

Loads the role only for its defaults, then runs one read-only shell script on the patch node. It shows the latest run (or zdlra_run_id): status, done and skipped phases, the approval, and, if a detached command is running, its PID and the last lines of its log. -e show=report prints report.txt.

4. Inside a phase

Every phase goes through run_phase.yml, which makes the same checks zdlra_patch.sh makes around a phase, then includes phase_<name>.yml.

Within a phase, a step that changes the appliance usually goes: show the command (and stop there in a dry run), look for an earlier attempt's result, ask you to type YES (confirm.yml, unless zdlra_confirm_steps=false), run it through racli_step.yml or patchmgr_step.yml, check its log, then read the versions.

5. How long commands are protected from being killed

An Ansible task that runs for hours over ssh would die with the connection, and async jobs are tied to Ansible's own bookkeeping. So patchmgr, the racli upgrade steps and Oracle's precheck run through zdlra_detached.sh, and detached.yml only talks to that helper.

  • start refuses to start a second copy. With a result left (LOG.rc not yet collected), it reports PENDING <rc> and that result is used, unless --fresh (always used for checks, such as the precheck and patchmgr prereq checks).
  • poll prints STATE=running|done|gone RC= LINES= ELAPSED=. gone means no exit status and no live process: it was killed or the node rebooted. Ansible records that as exit 99, so the next attempt starts it again.
  • Two waits. The first until loop runs to the step's warn time (for example 240 minutes for ra_update). Past that it prints a warning and keeps waiting, up to zdlra_wait_max_hours (12). Past that it stops watching and fails, saying the command is still running and how to pick it up.
  • collect renames LOG.rc once its result has been used, so a later attempt runs the step again. A successful patch or upgrade is not collected until it is recorded in steps_done, so it can never run twice.
  • running lists any patchmgr run, racli upgrade step or Oracle precheck on the node (an awk port of the script's find_long_command). refuse_if_running.yml uses it so nothing starts over another long command, except this run's own step of the same phase, which is waited for instead.

What each phase does and how it decides success matches the shell script; the main README has the full table. Here is where each lives and what to know about the Ansible side.

7. Compute nodes

The compute nodes are patched from the jump server, as the jump script does, because the patch node itself reboots. The play's host stays the patch node, but every compute task is delegated to a runner or a target node.

For each pass, compute_pass.yml:

  1. Skips the pass if the controller record lists it in compute_done.
  2. On the runner, creates /radump/zdlra_compute/<run id>/ and writes a db_nodes file holding only the target.
  3. Reads where the runner's jobs stand and the target's version. A target already on TARGET_COMPUTE_VERSION is not upgraded again.
  4. Runs patchmgr -dbnodes ... -precheck (fresh each time), checks it with compute_check.yml, then -upgrade. Both run detached on the runner, with the PID file and log in the runner's compute folder. The check needs no FAILED lines, exit 0, a completed run and every node in state SUCCESS. A run that ended badly with exit 0 is recorded as exit 98, so it starts again next time. SUCCESS WITH WARNING(S) is accepted and the warnings shown, unless zdlra_compute_pause_on_warnings.
  5. Waits for the target's imageinfo to show the target version, then for the node to be ready (wait_for_connection, then zdlra_node_ready_cmd: a database pmon running).
  6. Records the pass in the controller's JSON file.

After the last pass the patch node has rebooted, so the playbook waits for it and reads the run's records again before going on to the switches.

8. When something goes wrong

Any failed task jumps to the rescue, which runs failed.yml:

  • Writes failed in <phase> to the run's status. A refusal before a phase starts (approval missing, a long command running) leaves the status as it was, as the script does.
  • Prints the command to carry on once the problem is fixed: the same playbook with -e zdlra_run_id=<id>. Finished phases are skipped.
  • Only if you mean to abandon the run, it lists how to undo what was done: resume the paused replication servers (--tags resume), resume the OEM jobs and end the blackout (oem.yml). It does not do any of this itself.

9. How approval works

  1. approve.yml works out a fingerprint (fingerprint.yml): a SHA-256 of the failure and warning name lists plus staged=<archive sha256>.
  2. It shows the review (failures, waived ones, warnings, exit code, the staged archive and its SHA-256) with pause, and waits for APPROVE. With no terminal the answer is empty, so the run stops. Nothing skips this.
  3. It saves precheck_approval.txt in the run folder: who (SUDO_USER, USER or id -un, at the jump server's host name), when, precheck_dry_run, the counts and the fingerprint.
  4. Before the blackout and before every patch phase, require_approval.yml reads it back and refuses if it is missing, from a dry run when this is a real run, older than zdlra_precheck_approval_max_age_hours (24), or if the fingerprint worked out now differs.

The YES confirmations before each racli and patchmgr step are separate (confirm.yml) and can be turned off with zdlra_confirm_steps=false. The approval cannot.

10. The OEM blackout and jobs

  • Login (roles/oem/tasks/login.yml): emcli sync, or a login with vault_oem_em_password under no_log.
  • Blackout (blackout.yml): the name is kept in ~/zdlra_ansible_state/<appliance>.blackout. Before creating one it asks EM whether the recorded one is over; only a clear "ended", "stopped" or "expired" counts. It refuses while another is on. Stop retires the record with a timestamp.
  • Jobs (jobs.yml): sr_jobs_new.ksh only writes a script with one emcli command per job. The role finds the one script it just wrote, runs it to a .log, and checks each job has a "successfully" line. Missing ones are warnings, none at all is a failure.

12. What a dry run really does

A dry run (the default, or --check) still connects, reads and checks. It changes nothing on the appliance or in OEM.

Runs for realOnly shown
racli version and status, imageinfo, dcli reads, switch versions, SQL queries, the free space check, emcli login and get_blackout_reasons, and Oracle's precheck (it is not read-only, but it is what the approval is about)racli upgrade steps, every patchmgr, pausing and resuming replication, create_blackout, stop_blackout, suspending and resuming OEM jobs

A dry run writes the run folder, the precheck results and an approval marked precheck_dry_run=1, which a real run will not accept. It records no phase as done.

13. A real run, traced

A real run on the stand-in appliance, with every step in order. jump is the playbook on the jump server, node a task on a compute node, oem an OEM step, you the operator.

  1. youStart it in tmux

    ansible-playbook zdlra_patch.yml -e zdlra=zdlra01 -e zdlra_execute=true --ask-vault-pass

  2. jumpSetupsetup.yml

    Group zdlra01 found, patch node zdlra01db01. User is root, racli is there. Helpers copied to both nodes. A new run ID from the node's clock. Staged record and patch.conf_<SR> read.

  3. oemOEM checkoem/tasks/blackout.yml

    emcli login, the reason is a known one, targets set. Nothing created.

  4. nodeprecheck: quick checksphase_precheck.yml

    racli version and status, staged archive present, free space, SQL login as raAutomation.

  5. nodeOracle's precheck, detachedprecheck_script.yml, detached.yml

    start --fresh prints STARTED. Polled every 30 s until STATE=done RC=0. Summary: 0 failures, 1 warning.

  6. nodePlanplan.yml

    Replication pair RA2DR, 0 incoming backups, RA files present, cell and switch versions against their targets.

  7. youReview and type APPROVEapprove.yml

    precheck_approval.txt saved with the fingerprint.

  8. oemBlackout and jobschangeszdlra_patch.yml

    Approval checked. create_blackout, name recorded; sr_jobs_new.ksh generated and run, every job suspended. Both recorded in the controller JSON.

  9. nodequiescechanges

    RA2DR paused and written to replication_paused.txt. No incoming backups to wait for.

  10. nodesnapshot, ra_preinstall, ra_alter, ra_updatechangesracli_step.yml

    Each: approval checked, nothing else running, type YES, racli run detached, success line found, phase recorded.

  11. nodecellschangesphase_cells.yml

    Cells not on target. Prereq check passed, so no reset. -patch, then cells_patch in steps_done, then every cell on target.

  12. nodecomputechangescompute_pass.yml

    db01 upgrades db02 (precheck, upgrade, version, ready), then db02 upgrades db01. Each pass recorded on the jump server. Waits for db01 to come back.

  13. nodeswitcheschanges

    RoCE precheck, upgrade, then each switch's version. Admin switches skipped (off).

  14. nodepostcheck, resume, report

    Every component OK in the version table. RA2DR resumed, resumed_at written. report.txt written.

  15. oemOEM finishchanges

    Jobs resumed, blackout stopped and its record retired. oem_finished_at recorded.

  16. nodeverify, finish

    New backups and replication arrived after resumed_at. Status completed, the report printed.

The same run was also tested with Ansible killed during ra_update. racli kept going; running the same command with -e zdlra_run_id=<id> printed "Already running from an earlier attempt ... waiting for it, not starting it again", and the run finished with a single ra_update.log.
