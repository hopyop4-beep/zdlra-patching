How the ZDLRA patching scripts work

A walkthrough of the code on main at v0.7.8: what runs where, which function calls which, and what happens when something breaks. Numbers after a function name are line numbers in that script at this version.

Ground rules the code is built around

Long commands are never killedracli, patchmgr and the Oracle precheck run in their own session. No signal or dropped connection reaches them, and the scripts never stop them.
Nothing runs twice by accidentBefore a repeat patch, the real versions are read. Results left by an earlier attempt are used instead of running again.
Files hold the stateEverything needed to carry on is on disk, so any script can die and be picked up.
No change without approvalPatch phases refuse unless the precheck is approved, under 24 hours old, and unchanged.
Dry run by defaultOnly -x changes anything.
On failure, stop and holdBlackout and suspended jobs stay in place until you decide.
changes somethingmain stepguard or stopyou, or a side note

1. Who runs what

There are four scripts plus your own OEM job script. zdlra_patch.sh does the patching on node 1. zdlra_patch_run.sh supervises from the jump server, because only the jump server has OEM and only it survives every node reboot.

How the two main scripts talk

The jump script never reads the node's files directly. It runs zdlra_patch.sh over ssh with these options and reads what it prints.

3. Inside the jump script

All three ways of starting it end up in the same sequence. The state file decides where a pickup rejoins.

watch_until_done has two modes. While the precheck runs it reads the status word only. After that it calls node_state, which compares the node's Done: list with the phases expected, because any command run by hand that works writes completed. Ctrl-C at any point goes to on_interrupt, which stops the watching and prints what to run next for the current WATCHING value: precheck, jobs, patch, compute or verify.

4. Inside the node script

Every phase is a function named phase_<name>, called by name from the loop. Adding a phase means adding it to ALL_PHASES and writing that function.

The background hand-off

start_background writes the child's pid into the lock before the parent exits, so the lock never looks stale. The child runs with ZDLRA_LOCK_FROM set to the parent's pid and --bg-child, which also sets ASSUME_YES, so it never prompts. That's why approval has to happen before patch phases start.

5. How long commands are protected from being killed

Two flags change run_detached. DETACHED_FRESH=1 ignores any leftover result and always runs, which the prechecks use because an old pass says nothing about now. DETACHED_QUIET=1 doesn't show or copy the output, which the Oracle precheck uses because it's long and has its own file.

Why the precheck has to undo ra_preinstall

The Oracle precheck rolls back the RPM that preinstall installs. So phase_precheck calls phase_undone ra_preinstall, unless ra_update has already finished. Any later rerun of the precheck therefore runs preinstall again too.

7. Compute nodes

This is the only patching the node script doesn't do, because the node it runs on reboots. The jump script starts patchmgr on one node to upgrade another, then polls it over ssh through the reboot. It runs after the RA upgrade and cells, and before the switches.

What --continue does, in order

  1. Jump: take_run_lock, load_run_settings, refuse_if_abandoned.
  2. Jump: step_pickup_unstarted if started=0, then step_continue. If nothing is running and phases are left, it calls start_stage with the stage's phases and continue.
  3. Node: main removes everything in phases_done, so only unfinished phases run.
  4. Node: approval is checked again. If it's now over 24 hours old, the run refuses and you need a new precheck.
  5. Inside a phase: steps_done, pending_result and the version checks stop repeat patches. racli update carries on from where it stopped.
  6. Jump: carries on with the rest. The existing blackout and suspended jobs are kept.

9. How approval works

  1. phase_precheck writes precheck_passed once there are no blocking items.
  2. approve_precheck, in a background run, sets the status to awaiting approval. The jump script sees this and calls step_approve.
  3. The review shows failures, warnings, exit code and archive. Typing APPROVE writes precheck_approval.txt: who, when, and a fingerprint.
  4. require_approval then runs before every patch phase. It refuses if there's no file, if a real run has a dry-run precheck, if it's over PRECHECK_APPROVAL_MAX_AGE_HOURS, or if the fingerprint no longer matches.
  5. The fingerprint covers the failure names, the warning names and the staged archive's SHA-256. So re-staging another archive after approval is caught.
  6. Running the precheck again deletes the old pass and approval first.

12. What a dry run really does

  • Really runs: ssh checks, emcli login check, reading the staged record and versions, and read-only SQL. The Oracle precheck also really runs, without PRECHECK_EVENT_ARGS, and you still approve it.
  • Only prints: blackout, OEM job commands, SQL that changes something, racli steps, patchmgr commands.
  • Not saved: phases_done is not written, so the jump relies on the status word. A dry run can't be continued as a real one, and a dry-run approval is refused by a real run.

13.6 Waiting for the precheck, and approving it
